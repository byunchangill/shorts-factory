# 상품 정보·리뷰 수집 (product-crawl)

상품 URL과 잡을 받아 **제품 정보 + 구매자 리뷰**를 모아 `product.json`에 채운다.
대본 요청서의 「3. 제품 정보」가 그 JSON을 통째로 싣기 때문에, 여기까지만 채우면
대본을 쓰는 어느 경로에서도(Claude Code · API 자동 · 웹 챗 복붙) 같은 재료를 본다.

## 규칙은 이 문서가 아니라 코드에 있다

**직접 크롤링하지 않는다.** 서버 엔드포인트 하나를 부른다:

```
POST /api/jobs/{jobId}/product/crawl   { "url": "https://..." }
```

수집 규칙을 산문으로 적어두면 지키는 AI와 안 지키는 AI가 갈리고, **안 지킨 것을 아무도
모른다.** 그래서 아래는 전부 코드가 강제한다 — 이 스킬이 할 일은 부르고 결과를 읽는 것뿐이다.

- `validatePublicUrl` (`pipeline/productCrawl.ts`) — 루프백·사설 IP·링크로컬·`user:pass@`·
  http가 아닌 주소를 거부한다. **서버가 그 주소로 요청을 보내기 때문이다**
- `tools/crawl/collect_product.py` — robots.txt를 실제로 읽어 `can_fetch`를 확인하고,
  `crawl_delay`(최소 1초)를 지키고, **공개 접근 사다리 3단에서 멈춘다**
  (`Fetcher → FetcherSession → DynamicFetcher`, `impersonate=None`).
  🔴 CAPTCHA를 풀지 않고 브라우저인 척하지 않는다. 우회는 사람이 정할 일이다
- 응답 400은 **왜 막혔는지**를 갈라 말한다. 그 문장을 사용자에게 그대로 전한다 —
  robots가 막은 것과 사이트가 봇을 막은 것은 사용자가 할 일이 다르다

수집 런타임(Scrapling)은 별도 저장소(`byungjunjang/web-crawler`)의 `.venv`다. 앱이
형제 폴더 → 홈 아래 순으로 찾고, 다른 자리면 설정의 `crawlerPath`로 지정한다.
준비 상태는 `npm run doctor`의 **「상품 수집」** 항목이 뽑힌 경로와 함께 보여준다.

## 처리 순서

1. **잡을 확정한다.** 경로나 잡 id를 안 받았으면 되묻는다 — `product/`는 잡마다 따로다
2. **서버가 떠 있는지 본다** (`:4310`). 안 떠 있으면 `npm run dev`를 안내하고 멈춘다
3. **엔드포인트를 부른다.** 응답은 `{ product, fetcher, warnings }`
4. **막혔으면 그 문장을 그대로 전한다.** 되지도 않을 우회를 시도하지 않는다.
   `다시 시도해도 같습니다`가 들어 있으면 다시 부르지 않는다
5. **보고한다.** 리뷰 몇 개를 어디서 모았는지(`reviews.source`), 어떤 fetcher로 닿았는지,
   못 얻은 칸이 무엇인지. 🔴 **리뷰가 0개면 0개라고 말한다** — 빈 칸은
   「불만이 없는 제품」으로 읽힌다

## 막혔을 때 — 저장한 HTML이 정답이다

쿠팡처럼 자동 접근을 막는 사이트는 **robots.txt조차 HTTP 403**이다 (2026-09-07 실측).
이때 우회하지 말고 이 길로 간다:

1. 브라우저에서 상품 페이지를 연다
2. `Ctrl+S`로 페이지를 저장한다 (HTML)
3. 잡 화면의 **제품자료**에 그 파일을 올린다
4. **「제품정보 추출」** 요청서를 발행한다 — 첨부 자료를 읽어 같은 `product.json`을 만든다
   (`reviews` 칸 포함)

사람이 브라우저로 연 페이지를 저장하는 것은 차단을 뚫는 것이 아니다. 그래서 이 길만 안내한다.

## 결과를 어떻게 쓰나

앱은 `count`·`avgRating`·`quotes`·`source`·`collectedAt`만 채운다.

🔴 **`praises`·`complaints`는 비워 둔다.** 칭찬과 불만을 가르는 것은 판단이고 앱은 그
판단을 하지 않는다 — 어림짐작으로 채우면 「검사했다」는 잘못된 안심만 준다
(얼굴 검출을 자동으로 안 하는 것과 같은 자리). `quotes`에는 **별점이 앞에 붙은 원문**이
들어가므로 낮은 별점을 골라낼 수 있다. 가르는 일은 대본·제품정보 추출 요청서가 한다.

🔴 **리뷰는 구매자 의견이지 제품 사실이 아니다.** 효능·사양·성능 주장의 근거로 쓰지
않는다 — 「~라고 하더라」는 화법만 바꾼 같은 주장이다. 쓸 수 있는 자리는 **단점 씬의
재료**와 **말투의 온도** 둘뿐이고, 요청서가 그 문장을 값과 같이 싣는다.

## 금지 사항

- **직접 크롤링하지 않는다.** `WebFetch`·`curl`·직접 만든 스크립트로 상품 페이지를 긁지
  않는다 — 그러면 robots 확인도 요청 간격도 사다리도 통째로 건너뛴다
- 400 응답을 받고 **다른 방법으로 같은 페이지를 다시 시도하지 않는다**
- `job.json`·`packet.json`·`clip.json` 등 상태 파일을 건드리지 않는다 (서버 전용)
- `product.json`을 파일로 직접 쓰지 않는다. 엔드포인트나 요청서를 탄다 —
  둘 다 zod 검증과 `writeJsonAtomic`을 지나간다
- 리뷰 문장을 **지어내거나 다듬지 않는다.** 작성자 이름·아이디·사진은 애초에 안 가져온다
- 수집한 리뷰나 페이지 이미지를 씬 이미지·짤방으로 쓰지 않는다 — 그 경로는 출처 5필드가
  따로 필요하다 (CLAUDE.md 「소재의 출처를 적지 않으면 조립이 안 된다」)

## product.json의 리뷰 칸

```json
{
  "reviews": {
    "count": 60,
    "avgRating": "4.6",
    "praises": [],
    "complaints": [],
    "quotes": ["평점 2: 배터리가 십오 분이면 끝나요"],
    "source": "shop.example.com 상품페이지 60개 (페이지 표기 312개)",
    "collectedAt": "2026-09-07"
  }
}
```

스키마는 `shared/types.ts`의 `ProductReviewsSchema` 하나가 출처다.
