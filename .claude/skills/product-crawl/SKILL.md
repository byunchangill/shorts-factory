# 상품 정보·리뷰 수집 (product-crawl)

상품 URL 하나와 잡을 받아 **제품 정보 + 구매자 리뷰**를 모아 `product/`에 앉힌다.
대본 요청서의 「3. 제품 정보」가 `product.json`을 통째로 싣기 때문에, 여기까지만 채우면
대본을 쓰는 어느 경로에서도(Claude Code · API 자동 · 웹 챗 복붙) 같은 재료를 본다.

## 왜 리뷰인가

- **단점 씬이 리뷰에서 나온다.** menu-b는 단점 씬 1개가 필수인데(`isDownside`), 상세페이지에는
  단점이 없다. 파는 쪽이 쓴 글이기 때문이다. 실제 불만은 리뷰에만 있다
- **썰형의 말투가 리뷰에서 나온다.** 커뮤니티체의 온도는 지어낸 문장이 아니라 실제 표현이다
- 🔴 **리뷰는 구매자 의견이지 제품 사실이 아니다.** 효능·사양·성능 주장의 근거로 쓰지 않는다 —
  「~라고 하더라」는 화법만 바꾼 같은 주장이다. 쓸 수 있는 자리는 `complaints`와 `quotes` 둘뿐이고,
  요청서가 그 문장을 그대로 싣는다 (`packets.ts` 3절)

## 수집기는 이 저장소에 없다

수집은 **별도 저장소의 `web-crawler` 스킬**이 한다 (https://github.com/byungjunjang/web-crawler).
정찰(agent-browser) → 수집(Scrapling/Playwright) → 검증 → 도메인 프로필 저장까지가 그쪽 일이고,
이 스킬은 **그 결과를 이 앱의 자리에 앉히는 일**만 한다. 수집 방법·차단 대응·프로필 재사용은
그 저장소의 `SKILL.md`를 따른다.

저장소를 **경로로 찾는다** (설정에 절대경로를 박지 않는 것과 같은 결):

1. 이 저장소의 형제 폴더 — `../web-crawler`
2. 홈 아래 — `~/web-crawler`
3. 위 둘이 없으면 사용자에게 어디에 받았는지 묻는다. 없다면 `git clone` 위치부터 정한다

파이썬은 그 저장소의 `.venv`를 쓴다 — 윈도우는 `.venv\Scripts\python.exe`, 나머지는 `.venv/bin/python`.
동작 여부는 `python scripts/preflight.py`가 CORE/agent-browser로 갈라 답한다.

## 처리 순서

1. **잡을 확정한다.** `workspace/{menu}/{project}/jobs/{jobId}/`. 경로를 안 받았으면 되묻는다 —
   product 폴더는 잡마다 따로다
2. **URL의 약관·robots를 먼저 본다.** 크롤러 저장소가 그 판단 절차를 들고 있다. 🔴 **차단을
   기술적으로 우회하는 지점에서는 사용자에게 확인을 구한다.** 그 저장소의 규칙이고 여기서도 같다
3. **수집한다.** 상품 정보(제품명·가격·카테고리·사양·기능)와 리뷰를 모은다.
   - 리뷰는 **최신순**으로 모은다. 상위 노출 리뷰는 걸러진 표본이다
   - 별점 낮은 리뷰를 반드시 포함한다 — 단점 씬의 재료가 거기 있다
   - 몇 개를 어떤 정렬로 모았는지 적어둔다. `reviews.source`가 그 칸이다
4. **원본을 `product/crawl/`에 남긴다.** 수집 결과 파일(xlsx·json·md 무엇이든)을
   `workspace/{menu}/{project}/jobs/{jobId}/product/crawl/` 아래로 **복사**한다.
   요약이 근거를 잃지 않게 하는 자리이고, 요청서가 첨부파일 목록에 자동으로 싣는다
5. **`product.json`을 채운다.** 서버가 떠 있으면(`:4310`) API로 넣는다 — zod 검증과 원자적 쓰기를
   그대로 탄다:
   - 먼저 `GET /api/jobs/{jobId}/product`로 **지금 값을 읽는다**
   - 그 위에 새로 얻은 칸만 얹어 `PUT /api/jobs/{jobId}/product`로 보낸다.
     🔴 **PUT은 통째로 덮어쓴다** — 읽지 않고 보내면 사람이 손으로 적어둔 칸이 사라진다
   - 서버가 안 떠 있으면 4번까지만 하고, 화면의 **「제품정보 추출」** 요청서를 발행하라고 안내한다.
     그 요청서가 `product/`의 자료를 읽어 같은 `product.json`을 만든다 (`reviews` 칸 포함)
6. **보고한다.** 리뷰 몇 개를 어디서 모았는지, `complaints`에 무엇이 잡혔는지, 못 모은 것이
   무엇인지. **리뷰가 0개면 0개라고 말한다** — 빈 칸은 「불만이 없는 제품」으로 읽힌다

## 금지 사항

- `job.json`·`packet.json`·`clip.json` 등 상태 파일을 건드리지 않는다 (서버 전용)
- `product.json`을 파일로 직접 쓰지 않는다. API(`PUT`)나 「제품정보 추출」 요청서를 탄다 —
  둘 다 zod 검증과 `writeJsonAtomic`을 지나간다
- 리뷰 문장을 **지어내거나 다듬지 않는다.** `quotes`는 원문 그대로다
- 리뷰에서 **개인을 식별할 수 있는 것**(작성자 이름·아이디·사진)은 가져오지 않는다.
  필요한 것은 내용이지 누가 썼는지가 아니다
- 수집한 리뷰를 씬 이미지나 짤방으로 쓰지 않는다 — 그 경로는 출처 5필드가 따로 필요하다
  (CLAUDE.md 「소재의 출처를 적지 않으면 조립이 안 된다」)

## product.json의 리뷰 칸

```json
{
  "reviews": {
    "count": 60,
    "avgRating": "4.6",
    "praises": ["흡입력이 생각보다 세다", "무선이라 계단 청소가 편하다"],
    "complaints": ["배터리가 십오 분쯤이면 끝난다", "먼지통이 작아 자주 비워야 한다"],
    "quotes": ["소리는 좀 크네요 애기 있는 집은 낮에만"],
    "source": "쿠팡 상품평 최신순 60개",
    "collectedAt": "2026-09-06"
  }
}
```

스키마는 `shared/types.ts`의 `ProductReviewsSchema` 하나가 출처다. 칸을 늘리려면 거기서 늘린다.
