# 쇼핑쇼츠 콘텐츠 팀

리서치 → 대본 → 검수 → 패키징을 전문 에이전트 4명이 나눠 맡는다. 단일 AI가 한 번에 쓰는 것보다 느리지만, **검수 게이트가 있어 품질이 수렴한다**.

## 실행 모드

**에이전트 팀.** 검수자가 대본가에게 직접 반려 피드백을 보내고 대본가가 재작성하는 루프가 핵심이라, 팀 통신이 필요하다.

모든 Agent 호출에 `model: "opus"`를 명시한다. 단, `shorts-qc`는 검증 스크립트를 실행해야 하므로 `subagent_type: "general-purpose"`를 쓴다.

## Phase 0: 컨텍스트 확인

시작 전에 실행 모드를 판별한다.

| 상황 | 모드 |
|---|---|
| `_workspace/` 없음 | **초기 실행** — Phase 1부터 |
| `_workspace/` 있음 + 부분 수정 요청 ("대본만 다시") | **부분 재실행** — 해당 에이전트만 |
| `_workspace/` 있음 + 새 제품/요청서 | **새 실행** — 기존을 `_workspace_prev/`로 옮기고 처음부터 |

부분 재실행 매핑: 리서치 → 리서처만 / 대본 → 대본가+검수자 / 검수 → 검수자만 / 업로드킷 → 패키저만

## Phase 1: 입력 판별

두 가지 진입 경로를 자동 분기한다.

### 연동 모드 (요청서 경로가 주어짐)

`workspace/menu-a/.../requests/p03-script` 같은 경로를 받으면:

1. `request.md`를 읽는다 — 지침·제품정보·소재현황·산출물 명세가 모두 들어 있다
2. `packet.json`의 `resultSpec`으로 산출물 파일명과 스키마를 확인한다
3. 최종 산출물은 그 폴더의 `result/`에 쓰고, **마지막에 `result/.done`을 만든다** (서버가 감지해 자동 반영)

### 독립 모드 (제품명만 주어짐)

요청서 없이 "무선청소기 쇼츠 만들어줘"처럼 들어오면:

1. 프로젝트 지침이 있으면 읽는다 (`workspace/menu-*/{제품}/guidelines/`)
2. 산출물은 `_workspace/`에만 남기고 사용자에게 보고한다
3. 웹앱에 반영하려면 요청서 경로가 필요하다는 점을 안내한다

## Phase 2: 팀 구성 및 실행

```
TeamCreate("shorts-content", [shorts-researcher, shorts-scriptwriter, shorts-qc, shorts-packager])
```

작업 흐름과 의존 관계:

```
리서처 ──→ 대본가 ──→ 검수자 ──→ 패키저
              ↑          │
              └──반려────┘  (최대 3회)
```

`TaskCreate`로 의존성을 걸어 순서를 보장한다. 리서치가 끝나기 전에 대본가가 시작하면 재료 없이 쓰게 된다.

### 단계별 산출물

| 단계 | 담당 | 산출물 |
|---|---|---|
| 1 | 리서처 | `_workspace/01_research.md` |
| 2 | 대본가 | `_workspace/02_script_draft.json` |
| 3 | 검수자 | `_workspace/03_qc.md` (85점 게이트) |
| 4 | 패키저 | `_workspace/04_upload_kit.md` |

### 검수 게이트

- 85점 이상 → 패키저로 진행
- 85점 미만 → 대본가에게 반려, 재작성 후 재검수
- **3회 반려 시** → 팀을 멈추고 사용자에게 보고한다. 같은 지적이 반복되면 요구사항이나 소재 자체에 문제가 있을 가능성이 크다

## Phase 3: 산출물 반영

### 연동 모드

1. 승인된 대본을 `resultSpec`이 지정한 파일명으로 `result/`에 쓴다 (보통 `script.json`)
2. 업로드킷 요청서였다면 `result/upload-kit.md`
3. **`result/.done` 빈 파일을 마지막에 만든다**
4. `result/` 밖의 어떤 파일도 건드리지 않는다 — `job.json`, `packet.json`은 서버 전용이다

### 독립 모드

`_workspace/`의 산출물 경로를 사용자에게 보고한다.

## 데이터 전달

- **태스크 기반** — 진행 상황과 의존 관계
- **파일 기반** — `_workspace/`의 중간 산출물 (감사 추적용으로 보존)
- **메시지 기반** — 검수 반려 사유, 리서치 요약

파일명 규칙: `{순번}_{에이전트}_{산출물}.{확장자}`

## 에러 핸들링

| 상황 | 대응 |
|---|---|
| 유튜브 API 키 없음/쿼터 초과 | 리서처가 WebSearch로 전환. 중단하지 않고 "리서치 근거 제한적" 명시 |
| 소재(클립) 0개 | 대본가를 멈추고 사용자에게 보고. 클립 ID를 지어내지 않는다 |
| 제품 정보 비어 있음 | `product/` 첨부 자료를 직접 읽는다. 없으면 사용자에게 요청 |
| 검수 3회 반려 | 팀 중단, 회차별 점수 추이와 반복 지적 사항을 보고 |
| 요청서 스키마 불일치 | `request.md`의 산출물 명세를 우선한다. 이 스킬의 예시 스키마보다 요청서가 상위 |

에이전트 1회 실패는 재시도, 재실패 시 해당 산출물 없이 진행하고 보고서에 누락을 명시한다.

## 테스트 시나리오

### 정상 흐름

입력: `workspace/menu-a/무선청소기/jobs/20260810-001-1편/requests/p01-script`

1. 리서처가 유튜브 API로 "무선청소기 리뷰" 쇼츠 상위 25개 분석 → 훅 유형 분포 산출
2. 대본가가 소재 현황의 c01·c02와 프레임을 확인하고 5씬 대본 작성 (261자)
3. 검수자가 `check-script.mjs` 실행 → 시간 52초 적정, 금칙어 없음 → 소재 대조 통과 → 88점 통과
4. 패키저가 제목 5개·설명·해시태그·썸네일 문구 작성
5. `result/script.json` + `result/.done` 생성 → 서버가 감지해 대본 v1 반영

기대: 웹앱 요청서 카드가 "결과 도착"으로 바뀌고 씬별 대본 테이블이 표시된다.

### 에러 흐름

입력: 같은 요청서, 단 유튜브 API 키 미등록 + 소재 클립 0개

1. 리서처가 401을 받고 WebSearch로 전환, "API 미사용" 명시
2. 대본가가 소재 현황이 비어 있음을 확인 → **작업을 멈추고** 오케스트레이터에 보고
3. 오케스트레이터가 사용자에게 "다운로드를 먼저 완료하세요"라고 안내하고 종료

기대: 존재하지 않는 clipId가 들어간 대본이 만들어지지 않는다.

## 완료 후

사용자에게 결과를 보고하고 피드백을 받는다.

- 대본 품질에 불만 → 해당 에이전트의 스킬/정의를 고친다
- 워크플로우 순서 문제 → 이 오케스트레이터를 고친다
- 트리거가 안 걸림 → description을 확장한다

변경은 `CLAUDE.md`의 하네스 변경 이력에 기록한다.
