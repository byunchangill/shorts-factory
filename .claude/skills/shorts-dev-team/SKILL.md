# shorts-factory 개발 팀

이 프로젝트는 **규칙을 어겨서 서버가 죽은 전례**가 있다. 동시 쓰기로 상태 파일이 깨지고, 백그라운드 예외가 프로세스를 내리고, 상태 전이를 건너뛰어 사용자가 다음 단계로 못 갔다. 구현–검증–리뷰를 분리하는 이유가 이것이다.

## 실행 모드

**에이전트 팀.** 검증자가 실패를 발견하면 구현자에게 재현 방법과 함께 돌려보내고, 리뷰어가 규칙 위반을 지적하면 다시 구현자로 가는 루프가 필요하다.

Agent 호출 시 `model: "opus"`. 단 `dev-verifier`는 스크립트를 실행해야 하므로 `subagent_type: "general-purpose"`.

## Phase 0: 컨텍스트 확인

| 상황 | 모드 |
|---|---|
| `_workspace/dev_*` 없음 | **초기 실행** |
| 있음 + "지적사항 반영" | **부분 재실행** — 구현자부터 |
| 있음 + "검증만 다시" | **부분 재실행** — 검증자만 |
| 있음 + 새 기능 요청 | **새 실행** — 이전 `dev_*` 파일을 `_workspace_prev/`로 |

## Phase 1: 범위 확정

구현 전에 변경 범위를 정한다. 이 프로젝트에서 특히 확인할 것:

1. **파이프라인·상태 전이·요청서 왕복을 건드리는가?** → 그렇다면 검증자는 `npm run harness`를 반드시 돌려야 한다
2. **스키마를 바꾸는가?** → `shared/types.ts`만 수정. 기존 `workspace/` 데이터가 파싱되는지 확인 필요
3. **API 응답을 바꾸는가?** → 클라이언트 인터페이스도 함께 바뀌어야 한다 (경계면 대조 대상)
4. **외부 API를 붙이는가?** → 문서를 확인한다. 추측한 필드명은 리뷰에서 반려된다

요구사항이 모호하면 구현을 시작하지 말고 사용자에게 묻는다.

## Phase 2: 팀 구성 및 실행

```
TeamCreate("shorts-dev", [dev-implementer, dev-verifier, dev-reviewer])
```

```
구현자 ──→ 검증자 ──→ 리뷰어 ──→ 승인
   ↑          │          │
   └──실패────┘          │
   └──────지적───────────┘
```

| 단계 | 담당 | 산출물 |
|---|---|---|
| 1 | 구현자 | 코드 변경 + `_workspace/dev_01_changes.md` |
| 2 | 검증자 | `_workspace/dev_02_verify.md` |
| 3 | 리뷰어 | `_workspace/dev_03_review.md` |

### 검증 게이트

검증자가 실행해야 하는 것 — **읽고 판단하는 게 아니라 돌린다**:

```bash
cd server && npx tsc --noEmit
cd client && npx tsc --noEmit
npm test
npm run harness          # 파이프라인을 건드렸다면 필수
cd client && npx vite build   # UI를 건드렸다면
```

하네스는 포트 4310을 쓴다. `npm run dev`가 떠 있으면 즉시 중단되므로, 잔여 프로세스를 확인하고 정리한 뒤 실행한다.

### 리뷰 게이트

리뷰어가 발견 즉시 반려하는 항목:

- `mutateJob()`을 거치지 않은 상태 파일 읽기-수정-쓰기
- `.catch()` 없는 `void fn()`
- 두 칸 이상 건너뛰는 `transition()` (→ `advanceTo()` 사용)
- 셸 문자열 조립
- 응답에 마스킹 안 된 API 키
- `ytFetch`를 거치지 않은 유튜브 호출

3회 반려 시 팀을 멈추고 사용자에게 판단을 요청한다.

## 데이터 전달

- **파일 기반** — `_workspace/dev_*.md` (변경 근거 추적)
- **메시지 기반** — 실패 재현 방법, 지적 사항
- **태스크 기반** — 단계 의존성

## 에러 핸들링

| 상황 | 대응 |
|---|---|
| 하네스가 환경 문제로 실패 (도구 미설치) | 코드 문제와 구분해 명시. 코드 탓으로 돌리지 않는다 |
| 테스트가 불안정하게 실패 | 3회 재실행해 재현율 기록. 1/3이면 레이스 컨디션 의심 |
| 포트 4310 점유 | 잔여 프로세스 정리 후 재시도. 남의 서버에 붙어 엉뚱한 검증을 하지 않는다 |
| 규칙과 요구사항이 충돌 | 구현을 멈추고 보고. 규칙을 몰래 우회하지 않는다 |
| diff가 과도하게 큼 | 리뷰어가 규칙 위반을 우선 전수 확인, 설계 심사는 핵심 모듈로 한정하고 범위 축소를 명시 |

## 테스트 시나리오

### 정상 흐름

입력: "조립할 때 BGM을 깔 수 있게 해줘"

1. 구현자가 `assemble.ts`에 BGM 믹싱을 추가하고 `SettingsSchema`에 경로 필드 추가, 타입체크 통과
2. 검증자가 `npm test`(63건) + `npm run harness`(25단계) 실행 → 통과. 설정 API 응답과 `SettingsPage` 인터페이스 대조 → 신규 필드가 양쪽에 모두 있음 확인
3. 리뷰어가 diff 심사 → `void` 호출에 catch 있음, 스키마가 `shared/types.ts`에만 있음 → 승인
4. 오케스트레이터가 변경 요약을 보고

기대: 하네스가 통과하므로 기존 파이프라인이 깨지지 않았음이 보장된다.

### 에러 흐름

입력: "다운로드 완료되면 바로 대본 단계로 보내줘"

1. 구현자가 `transition(ref, 'scripting')`을 추가 (downloading → scripting은 세 칸)
2. 검증자가 하네스 실행 → 다운로드 후 상태가 멈춤. 서버 로그에서 "전이 불가: downloading → scripting" 확인 → 구현자에게 재현 방법과 함께 반려
3. 구현자가 `advanceTo(ref, 'scripting')`으로 수정
4. 검증자 재실행 → 통과, 리뷰어 승인

기대: 상태 전이 위반이 사용자에게 도달하기 전에 잡힌다.

## 완료 후

변경 요약과 검증 결과를 보고하고, 커밋·푸시가 필요한지 확인한다. 사용자가 승인하면 `feat/fix/refactor/docs/test` 접두어로 커밋한다.

규칙이 새로 생기거나 바뀌었으면 `CLAUDE.md`에 반영하고, 하네스 변경 이력에 기록한다.
